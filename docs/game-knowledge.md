# Game Knowledge bundles

A Game Knowledge bundle is the static facts about DCSS for one Crawl Version, as one JSON file: monsters with their melee attacks, holiness, resistances, action costs, the gear they may be made with, whether they are firewood, unique or have Nightvision, how clever they are, the terrain they can stand on, how crawl moves them and which blow up into torment as they die, item classes and sub-types with the message crawl gives as the player learns what an item they carry is, launchers, missiles, melee weapons and wands, how a weapon's name shows its brand, spells and the clouds they leave, skills, species with how undead each is, its size, whether it swims and the mutations it grows, the forms the player can take and the bodies they give, dungeon features with what each is to someone walking onto it, which are water and which are staircases, the values crawl gives a monster's attitude and threat rating and what the game waits for the player to do, the branches of the dungeon with the shallowest level crawl makes each monster on at random, what the game shows that tells the player's Lighting, holiness and speed and of the statuses that put them in danger, which of the player's items, spells and abilities are Ways Out, and which variant of each ported crawl formula the version uses. `crates/gk` defines the format and `tools/gk-extract` builds it from crawl's source at a release tag. The app ships the bundles in `crates/gk/bundles/`, built into the binary.

Webtiles sends monster, item and dungeon feature types, and a monster's attitude and threat rating, as crawl's C++ enum values, which crawl renumbers between versions. A bundle keys everything by its own version's values, so the webtiles Game Source decodes a game's monsters and items through the bundle for that game's Crawl Version. With no bundle for the version, nothing is decoded: monsters keep the name the game sends, and the Advisor knows nothing more about them.

Webtiles sends an item's true sub-type even when the player doesn't know it, so the source decodes it only once the player has identified the item's kind: the item is flagged identified, its name names its sub-type, or, unless it is an artefact, another item of its kind showed so earlier in the game, as crawl itself knows an artefact's kind only from the artefact. Crawl can identify a kind without resending a carried item of it, as when the player sees an identified item of the kind; then only its message says so ("You learned that … actually …"), and the source learns the kind from that.

## What the extractor reads

The extractor reads the source as a webtiles server's build compiles it: `TAG_MAJOR_VERSION` from `tag-version.h`, with `USE_TILE` and `USE_TILE_WEB` defined.

It reads only files crawl checks in, since CI checks crawl out at the tag without building it. A header crawl's build writes, such as `mon-mst.h`, isn't there, so an identifier only such a header defines is checked against the script that writes it (`util/gen-mst.pl` for `MST_GHOST`). CI checks out only the paths the extractor reads (the sparse checkout in `.github/workflows/ci.yml`), so a file it starts reading goes on that list too.

| Bundle part | From |
|---|---|
| monsters | `dat/mons/*.yaml`, numbered by `monster_type` in `monster-type.h`, described by `dat/descript/monsters.txt`; attacks, holiness (`MH_NATURAL` unless set, checked against `mon-holy-type.h`), the resistances a beam's damage meets as the file gives them (what holiness adds is the engine's), the `fighter`, `stationary`, `archer`, `prefer_ranged`, `two_weapons`, `unique`, `batty`, `maintain_range` and `flies` flags, habitat, intelligence, energy costs, spellbook and tile read as `util/mon-gen.py` reads them |
| how monsters move | which kinds are tentacles or tentacle segments, from the tables in `mon-tentacle.cc`; which have a special ability, from the cases of `mon_special_ability` in `mon-abil.cc`; and which `handle_monster_move` acts or moves for with code of its own and which step toward a foe that watches them only from beside them or only by chance (`_fungal_move_check`), ported by hand for each release series and each checked against the function in `mon-act.cc` that names it, with projectiles, which have the `projectile` flag, among those with code of their own |
| how monsters die | which blow themselves up into torment as they die, and so as they attack, ported by hand for each release series and checked against `explode_monster` in `mon-explode.cc`, which names them |
| monster firewood | crawl's `mons_class_is_firewood`: a monster with the `stationary` and `no_threat` flags, unless it is a tentacle or tentacle segment, from the tables in `mon-tentacle.cc`, or one of crawl's test monsters (`mons_class_is_test`), ported by hand for each release series |
| monster Nightvision | crawl's `monster::nightvision` for one of the kind carrying nothing: an `undead` holiness or the god `Yredelemnul` in its `dat/mons` file, or a kind `monster::umbra_radius` gives an Umbra in code, such as the death knight, ported by hand for each release series |
| Lighting signs | the status lights that backlight the player, the gods whose followers have a Halo, the statuses of a Halo of the player's own and what the names of halo gear hold, ported by hand for each release series and each checked against crawl's source (`duration-data.h`, `status.cc`, `religion.cc`, `art-data.txt`, `item-name.cc`), so a renamed one stops the extraction |
| holiness signs | the species crawl makes nonliving (`species::is_nonliving`) or counts as demonic (`player::undead_or_demonic`), the good gods (`is_good_god`), the forms `player::undead_state` makes undead, those `player::holiness` adds undead to and those `torment_player` halves torment for, and the status light of petrification, ported by hand for each release series (`HolinessRules` in `tools/gk-extract`), each species checked against the bundle's own, each form against `dat/forms`, and the torment-halving ones against `torment_player` in `spl-goditem.cc`, and each god and light against crawl's source (`religion.cc`, `duration-data.h`) |
| Way Out signs | which kinds of item, spells and abilities are Ways Out, each with what it does for the player (heals, escapes at once or after a delay, hinders monsters, hastens or strengthens) and whether it translocates or is invoked aloud; the statuses that stop the player reading, drinking, casting, using abilities, invoking or translocating, by the light or words the status pane shows; the statuses that stop each ability in particular; and the colour the ability menu greys out an ability in. Which are Ways Out and what stops each kind of use are the Advisor's own choice, ported by hand for each release series (`WayOutRules` in `tools/gk-extract`), with every item and spell checked against the bundle's own, every ability against its `ability_type` identifier in `Ability_List` (`ability.cc`) and every status against crawl's source (`duration-data.h`, `status.cc`). Each ability's own statuses are read from the code that checks it: its arm of `_check_ability_possible`'s `switch`, and the helpers that arm or its arm of `_do_ability`'s calls (`can_go_berserk` and `berserk` in `player-act.cc`, `_can_hop` and the like in `ability.cc`), taking each duration they read without negating it, with its light, or its words when it has none, from `duration_data`, and `beheld` as `fill_status_info`'s `Mesm`; which helpers to follow is ported by hand. The menu's colour is `COL_INAPPLICABLE` (`spl-util.h`), numbered by `COLOURS` (`defines.h`) |
| speed signs | what tells how fast the player moves, as `player_speed` and `player_movement_speed` (`player.cc`) read it: the status lights of the statuses that change it, ported by hand for each release series and each checked against `status.cc` or `duration-data.h`, and every other light the status pane may show, as telling nothing: each duration's light from `duration_data` in `duration-data.h`, and each light `fill_status_info` sets in `status.cc`, the words before what changes of one it builds as it draws it (`Torch` of `Torch (%d)`), with a light set in any way the extractor doesn't read failing the extraction; the mutations and banes that change it, ported by hand and read from `mut_data` in `mutation-data.h` and `bane_data` in `bane-data.h` with how the mutations screen (`A`) shows each and the messages crawl gives as it comes and goes (a bane's from `add_bane` and `remove_bane` in `mutation.cc`); the gods whose followers it slows and who walk on water, checked against `god-passive.cc` and `religion.cc`; and what the names of ponderous armour and the lightning scales hold, checked against `item-name.cc` and `art-data.txt` (`SpeedRules` in `tools/gk-extract`) |
| monster gear | what `give_item` (`mon-gear.cc`) may make a monster of each kind with to shoot, throw or zap, by chance: a launcher from the weapon specs `make_mons_weapon` draws from, throwing missiles, and a wand it will zap. The code around those tables is ported by hand for each release series (below) |
| launchers and missiles | `Weapon_prop` (the weapons trained by `SK_RANGED_WEAPONS`) and `Missile_prop` in `item-prop.cc`: damage and accuracy, a launcher's speed and a thrown missile's mulch rate |
| melee weapons | the rest of `Weapon_prop` but the retired blowgun, trained by `SK_THROWING`: damage, accuracy, speed, skill and reach, two squares for a weapon trained by `SK_POLEARMS` and one for any other, as crawl's `weapon_reach` gives a weapon that isn't an artefact, ported by hand |
| weapon brands | `brand_type` in `item-prop-enum.h`, each named as `weapon_brand_desc` (`item-name.cc`) names a weapon with it: by `weapon_brands_adj` before the weapon's name for a brand in `brand_prefers_adj`, such as `heavy`, and by `weapon_brands_verbose` after `of` otherwise, such as `flaming`. Brands crawl has retired, which it names `obsolescence`, are left out |
| wands | the spell each wand zaps, from `_wand_spells` in `spl-book.cc`, and the item sets crawl picks one wand of per game, from `item_sets` in `item-prop.cc` |
| monster spellbooks | `mspell_list` in `mon-spell.h`: each book's spells, how often each is picked and its slot flags. A book of `MST_GHOST` means each monster of the kind is given its own spells when made, which the bundle can't know |
| monster tiles | the tile lists in `rltiles/`, from `dc-player.txt`, read as crawl's tile build (`rltiles/tool`) reads them |
| item classes | `object_class_type` in `object-class-type.h`, and which classes hide which kind an item is until the player identifies it: crawl's `item_type_has_ids` (`item-name.cc`), ported by hand for each release series, each class checked against the enum; and the message crawl gives when the player learns the kind of an item they carry by seeing another of its kind identified (`seen_item`), ported by hand for each release series and checked against `item-prop.cc` |
| item sub-types | the sub-type enums in `item-prop-enum.h`, `potion-type.h` and `book-type.h`, named by the tables and name functions in `item-prop.cc` and `item-name.cc` |
| spells | `spelldata` in `spl-data.h`, numbered by `spell_type` in `spell-type.h`, with each spell's schools, range and power cap; constants such as `LOS_RADIUS` from `defines.h` |
| zaps | the zap a spell fires from `_spl_zaps` in `spl-zap.cc` (its first, for a spell listed twice), and that zap's flavour, flags and the damage dice and accuracy by power a monster and the player each fire it with, from `zap_data` in `zap-data.h` |
| spell clouds | the cloud a spell's beam leaves round where it ends, from `bolt::get_cloud_type` in `beam.cc`, its `cloud_type` checked against `cloud-type.h`; whether it is opaque, from `clouds` in `cloud.cc`, numbered by `cloud_type`; and whether the beam leaves it on every square it passes too, from the clouds `bolt::affect_place_clouds` places for the spell or its zap's flavour with no further condition |
| skills | `skill_type` in `skill-type.h`, each named by the first column of its row of `skill_titles` in `skills.cc`, as the skills screen names it |
| species | `dat/species/*.yaml`, with its `undead_type`, its `size` (medium unless set), whether it swims (`can_swim`) and its `mutations` by the experience level each comes at |
| forms | `dat/forms/*.yaml`, read as `util/form-gen.py` reads them: each form's status light, its `short_name` or its `enum` capitalised, its `holiness`, none unless set, its resistance to negative energy, `resists: neg`, 0 unless set, and the body it gives the player: its `move_speed` (10 unless set), `size`, `can_swim` and `changes_anatomy`. The form `none` shows no light and is left out, but its body is kept as the speed signs' body in no form |
| dungeon features | `feat_defs` in `feature-data.h`, numbered by `dungeon_feature_type` in `dungeon-feature-type.h`: each feature's name; its terrain from its `FFT_SOLID` flag and minimap colour (a solid door is a closed door, deep water and lava are crossed only by swimming or flying, and every other solid feature can't be walked onto); whether it is a staircase from the glyph it is drawn with, `<` or `>`; and whether it is water (`feat_is_water`), ported by hand for each release series and checked against `feat_is_shallow_water` and `feat_is_deep_water` in `terrain.cc`, which name it. The flag, minimap colours and glyphs read are each checked against their enum (`feature.h`, `map-feature.h`, `dungeon-char-type.h`). Crawl's code that seals a door or a staircase, and the staircase out of the dungeon, which ends the game rather than leading to a level, are ported by hand for each release series (`FeatureRules` in `tools/gk-extract`) |
| monster attitudes | `mon_attitude_type` in `mon-attitude-type.h` |
| monster threat ratings | `mon_threat_level_type` in `mon-util.h` |
| what the game waits for | `mouse_mode` in `defines.h`, read from its own declaration as `COLOURS` is: webtiles' `input_mode`, which tells when the game waits for the player's next command |
| branches | `branches` in `branch-data.h`, each with its `branch_type` identifier (`branch-type.h`) and the name webtiles gives the place a level of it is: its short name, with the article crawl's code gives some branches one level deep, ported by hand for each release series (`PlaceNamingRules` in `tools/gk-extract`) and checked against `tileweb.cc`, `branch.cc` and `english.cc`, so the Bazaar's levels are `a Bazaar`; and the shallowest of its levels crawl makes each monster on at random, from its entries in `population` (`mon-pick-data.h`), counting an entry that starts before the branch's first level as starting on it. Both tables must list one entry per branch in `branch_type`'s order, and every monster a population names must be in `monster_type` |
| danger signs | the words that describe poison that will kill the player, and the status lights of petrification, liquid fire and confusion, ported by hand for each release series (`DangerRules` in `tools/gk-extract`) and each checked against crawl's source (`status.cc`, `duration-data.h`) |

A monster's gear is given as crawl gives it to a monster made on D:3 or deeper, outside the Orcish Mines and not in a band: a goblin is then made with a sling one time in 12, which it never is on D:1, and an orc warrior with boomerangs one time in 20 rather than one in 9 in the Mines. Crawl's code around the gear tables, the cases of `make_mons_weapon`'s `switch` that give a ranged item, `_give_ammo` and `_give_wand` with what it calls, is ported by hand for each release series (`GearRules` in `tools/gk-extract`), with every monster, launcher, missile and wand it names checked against crawl's enums, and the crawl oracle's gear cases check the outcome against crawl's own `give_item`.

A bundle also names the variant of each ported crawl formula its version uses, such as `crawl-0.34` for a monster's to-hit or for which spell a monster picks, so the engine picks its code by name and never compares version strings. The extractor picks them by the release's series, so `0.34.1` gets the variants ported from crawl 0.34. A release in a series it has no variants for, such as a newer stable, a beta or trunk, stops the extraction rather than being read as 0.34, and so does a crawl whose monster data has changed shape, such as an attack with a field `mon-gen.py` 0.34 doesn't know. Adding a series means porting its formulas and gear code and naming them in `SERIES` in `tools/gk-extract`.

It understands only what those files use: `#if TAG_MAJOR_VERSION` conditionals, macros that build table entries, function-like or object-like, with their uses of other macros, `#` and `##`, enum initializers that are literals or earlier enumerators, `static const` maps and lists initialized in braces, table entries built by `_mon_hex_zap`, and damage and accuracy calculators whose template arguments are literals or integer `#define`s. Anything else stops the extraction with an error naming the file, rather than producing a wrong bundle. So does a crawl identifier the extractor's code names that crawl's source doesn't define, such as a monster crawl has renamed: the test `every_crawl_identifier_the_extractor_names_fails_the_extraction_once_crawl_renames_it` renames each in turn in the fixture and expects the extraction to stop, naming it.

## Building a bundle

```sh
git clone --depth 1 --branch 0.34.1 https://github.com/crawl/crawl /tmp/crawl
cargo run -p gk-extract -- /tmp/crawl --tag 0.34.1 --commit "$(git -C /tmp/crawl rev-parse HEAD)" \
  --tiles app/static/tiles > crates/gk/bundles/0.34.1.json
```

`--tiles` writes the image of every tile the bundle names into the app's `static/tiles/`, where the panel draws them from.

The extractor checks `--tag` and `--commit` against the checkout with git: the tag must point at the commit, which must be the one checked out, with no changes to tracked files. Each bundle records the crawl tag and commit it came from and crawl's license (ADR 0002). A new bundle also needs adding to `Library::shipped` in `crates/gk`.

## Tiles

A monster's tile is the image webtiles draws it with, named by its path in `rltiles` without the extension, such as `mon/animals/jackal`. Its tile enum is the one `util/mon-gen.py` gives it, and the tile lists say which image file that enum is drawn from. A tile crawl's build makes, by recolouring, mirroring, composing onto a background or turning into a corpse, has no file of its own, so the bundle names no tile for it.

Every tile file the bundle names ships, whatever its license. Most are CC0; the ones crawl's tile project lists as under an unknown license, from NetHack, or not agreed by their artist (`TILES_UNDER_UNKNOWN_LICENSE.md` in [crawl/tiles](https://github.com/crawl/tiles)) are not, and ship as part of crawl under its GPL (ADR 0002, `NOTICE`).

Crawl's build outlines the tiles listed under `%rim 1` in black: every transparent pixel beside a drawn one, up, down, left or right, becomes opaque black (`tile::add_rim` in `rltiles/tool/tile.cc`). The extractor does the same to those tiles as it writes them, so they look as they do in webtiles, and copies the rest unchanged. A file drawn both with and without the outline for different monsters stops the extraction, since the app ships one image per file. The panel draws a monster without a tile as its glyph.

Crawl's data gives some monsters the program bug's error tile (`misc/error`), which isn't a picture of them, so the extractor gives them no tile and doesn't ship the error image. No tile yet: crawl composes or recolours them at runtime. At 0.34.1 they are:

- program bug;
- black, yellow, green, purple, red, white, grey and pale draconian;
- tentacle and tentacle segment (the kraken's), eldritch tentacle and eldritch tentacle segment, starspawn tentacle and starspawn tentacle segment, snaplasher vine and snaplasher vine segment;
- hell lord and god wrath avatar.

## Tests

The tests in `tools/gk-extract/tests/extract.rs` cover the extractor (seam 3):

- A snapshot of the bundle built from `tests/crawl-0.34.1/`, crawl's files at 0.34.1 trimmed to a few entries each, and the tiles written from it, the outlined ones checked against `tests/outlined-by-crawl/`, made by crawl's own `rltiles/tool` code. They run everywhere, as do the checks of a release against a throwaway git checkout and of a release with no known formula variants.
- The shipped bundle and tiles are exactly what the extractor makes of crawl at its tag. It needs a crawl checkout, so it is ignored unless run with one; CI checks out crawl at the pinned commit and runs it:

```sh
DCSS_CRAWL_SOURCE=/tmp/crawl cargo test -p gk-extract -- --ignored
```
